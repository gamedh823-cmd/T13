# eval — 신호 감지 정확도 측정

프롬프트 신호 점검기의 신호 감지(`core.js`)가 얼마나 맞는지 재는 도구입니다.

| 파일 | 설명 |
|---|---|
| `build_labels.py` | 라벨 세트를 만드는 스크립트. 라벨을 고칠 때는 `labels.json`이 아니라 이 파일을 고치고 다시 실행합니다 |
| `labels.json` | 라벨 세트 116개(개발용 dev 96, 보류용 holdout 20). 문장마다 정답 신호 목록 |
| `score.js` | 채점. 신호별 정밀도·재현율·F1, 문장 종류별 일치율, 틀린 사례 |
| `baseline_dev.md` | 개선 전 기준선 결과(개발용) |
| `report.js` | 정확도 보고를 만든다: `node eval/report.js` → `report.json`, `report_data.js`(앱 화면이 읽음). 확신도 구간별 실제 정확도(보정)를 개발용+검증 문장 462개로 계산 |
| `real_use.json` | 실제로 앱에 넣어 본 문장(출처 표시). 합성·AI 초안 라벨과 섞지 않고 따로 잰다. `node eval/score.js --set real --engine model --thr 0.4` |

## 실행

```bash
node eval/score.js dev --errors      # 개발용 채점과 틀린 사례
node eval/score.js dev --md eval/result_dev.md
node eval/score.js holdout           # 보류용: 개선을 모두 마친 뒤 마지막에 한 번만
```

## 라벨 기준

신호 id는 `core.js` `analyze()`가 돌려주는 id와 같습니다.

- `debate` 토론 지시: 두 입장이 서로 주장·반박하게 하거나 토론 형식으로 풀게 하는 요청
- `persona` 전문가 역할: AI에게 직업·경력·역할을 주고 그 입장에서 답하게 하는 요청
- `majority` 다수 의견: 내 의견이 아니라 "대부분의 사람들은/여론은"을 묻는 질문
- `specific` / `vague` 이미지 요청: 색·배치·문구·분위기 등 요소가 3개 이상 적혀 있으면 specific, 그보다 막연하면 vague
- `cot` 풀이 과정 요구: 과정·이유·근거를 단계적으로 쓰게 하는 요청
- `fewshot` 예시 제시: 형식이나 말투를 보여 주는 예시·샘플을 함께 주는 경우
- `opinion` 내 의견 먼저: 질문자가 자기 생각을 먼저 밝히고 동의·평가를 구하는 경우
- `brainstorm` 열린 추천: 후보·아이디어·이름·장소·선물처럼 여러 선택지를 구하는 요청. "~하는 방법이 없을까 / 새로운 방법 / 어떻게 하면 좋을까"처럼 방법·조언·정보를 묻는 건 열린 추천이 아니다

문장 종류(`kind`): `pos` 신호가 분명한 문장, `para` 키워드 없이 돌려 쓴 문장, `multi` 신호가 여러 개, `neg` 신호 없는 평범한 문장, `negation` 신호를 "빼 달라"고 한 문장, `mention` 신호 단어를 언급만 한 문장(요청이 아님), `hard` 열린 추천과 헷갈리기 쉬운 문장(방법을 묻는 "없을까", 단어 언급, 후보를 구하는 요청).

정답은 문장이 실제로 요구하는 것을 기준으로 붙였고, 정규식을 보고 붙이지 않았습니다. 다만 초안을 쓰면서 규칙을 알고 있었으므로 `pos`·`specific`·`vague` 같은 쉬운 문장에서는 점수가 실제보다 높게 나올 수 있습니다.

## 한계

- 116개는 신호별로 4~14개뿐이라 한 문장이 점수에 크게 영향을 줍니다. 신호별 수치는 참고용입니다.
- 라벨은 한 사람(과 AI 초안)이 붙였습니다. 다른 사람이 붙인 라벨과의 일치율은 아직 재지 않았습니다.
- 보류용 20개는 개선이 끝나기 전에는 채점하지 않습니다. 모델 수정을 마친 2026-10-28에 한 번 쟀습니다: 정밀도 0.93, 재현율 0.93, F1 0.93(오탐 1건 "Make me a banner for my shop.", 놓침 1건 예시를 든 포스터 요청). 20문장이라 참고용입니다.
