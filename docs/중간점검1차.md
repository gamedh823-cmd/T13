# 중간 점검 1차 제출 — 신호 감지 정확도 개선

제출일: 2026-10-20 · 기반 앱(T13): https://gamedh823-cmd.github.io/T13/ · 소스: https://github.com/gamedh823-cmd/T13

## 이번에 만든 것

지난 과제(T13 프롬프트 신호 점검기)의 신호 감지는 정규식이었고, 얼마나 정확한지 재 본 적이 없었다. 이번에는 **정확도를 재는 도구를 만들고, 기준선을 재고, 학습한 분류기로 바꿔서 앱에 연결**했다.

1. **라벨 세트 116개와 채점 도구** (`eval/`): 문장마다 신호 정답을 붙였다. 신호 분명한 문장, 돌려 쓴 문장, 여러 신호, 신호 없는 문장, "토론하지 말고"처럼 신호를 빼 달라는 문장, 단어만 언급한 문장, 열린 추천과 헷갈리는 문장으로 나눴다. 개발용 96개와 보류용 20개로 나눠 두고 보류용은 마지막에 한 번만 잰다. `node eval/score.js`로 신호별 정밀도·재현율·F1과 틀린 사례를 낸다.
2. **기준선**(개선 전 정규식): 개발용 96개에서 정밀도 0.84, 재현율 0.80, F1 0.82. 특히 열린 추천은 정밀도 0.63이었다("엑셀에서 합계 구하는 방법이 없을까?"를 열린 추천으로 잡음). `eval/baseline_dev.md`에 틀린 사례와 함께 고정했다.
3. **학습 데이터 정확히 2000개** (`train/`): 합성 문장 1432개 + 직접 쓴 문장 291개 + 열린 추천과 헷갈리는 문장 277개. 학습 1634개, 학습에 쓰지 않은 검증 366개. 개인정보 없음, 평가용 라벨 문장은 자동 제외.
4. **글자 n-gram 분류기 학습과 앱 연결**: 학습한 가중치(`train/model.js`, 약 0.5MB)를 브라우저에서 서버 없이 돌린다. 모델을 못 불러오면 기존 규칙으로 돌아가 앱이 멈추지 않는다.
5. 테스트 44개(core 31, eval 5, ml 8) 모두 통과.

**결과** (개발용 96개, 같은 라벨·같은 채점)

| 엔진 | 정밀도 | 재현율 | F1 | 열린 추천 정밀도 | 어려운 문장 정답 |
|---|---|---|---|---|---|
| 기존 규칙(기준선) | 0.84 | 0.80 | 0.82 | 0.63 | 7/16 |
| 학습 모델(앱에 적용, 임계값 0.4) | 0.97 | 0.92 | 0.94 | 1.00 | 15/16 |

학습에 쓰지 않은 검증 세트에서의 F1(임계값 0.3): 처음 보는 표현(합성) 253개 0.93, 직접 쓴 새 말투 113개 0.85.

## 확인하는 방법 (3단계 이내)

1. https://gamedh823-cmd.github.io/T13/ 에 접속해서 입력칸에 `엑셀에서 합계 구하는 방법이 없을까?`를 넣고 `점검하기`를 누른다. "열린 추천 요청"에 체크가 **안 되고**(8가지 신호 중 0가지) 신호 없음 안내가 나오면 통과(예전 규칙은 열린 추천으로 잡았다).
2. 입력칸에 `고양이 이름 후보 좀 지어 줘`를 넣고 `점검하기`를 누른다. "열린 추천 요청"에 ✔가 나오고 "문장 전체의 맥락으로 판단했어요 (학습한 모델)"가 보이면 통과.
3. 저장소에서 `node tests/core.test.js && node tests/eval.test.js && node tests/ml.test.js`를 실행해 31개·5개·8개가 모두 통과하는지 보고, `node eval/score.js dev --engine model --thr 0.4`와 `node eval/score.js dev`로 학습 모델과 기준선 점수를 나란히 본다.

## 바뀐 점과 그 이유

- **감지 방식을 정규식에서 학습한 분류기로 바꿨다.** 앱에서 직접 써 보다가 "열린 추천"이 이상하게 자주 잡힌다는 것을 알게 됐다. 원인은 `없을까`, `새로운 방법`, `추천` 같은 단어만 보는 규칙이었다. 그런데 처음 만든 라벨 80개에는 이런 문장이 거의 없어서 점수(F1 0.87)에는 이 문제가 안 보였다. 그래서 헷갈리는 문장 20개를 라벨에 더해 다시 재 보니 열린 추천 정밀도가 0.63이었고, 이 구분을 학습 데이터에 넣어서 모델을 다시 학습했다.
- **"열린 추천"의 정의를 분명히 했다.** 후보·아이디어·이름·장소·선물처럼 여러 선택지를 구하는 요청만 열린 추천이고, "~하는 방법이 없을까"처럼 방법이나 조언을 묻는 것은 아니다. 라벨과 학습 데이터를 이 기준으로 맞췄다.
- **임계값을 0.3에서 0.4로 올렸다.** 0.3은 F1이 조금 더 높지만(0.95) 엉뚱한 신호가 붙는 오탐이 늘어서, 정밀도가 높은 0.4(정밀도 0.97)를 골랐다.
- **"AI 판별은 Workbench로" 계획은 접었다.** 수업용 AI(CLCO)는 Workbench 연결 승인이 필요한데 이 PC에서 연결이 되지 않았고, 데이터 다양화가 목적이라 직접 쓴 문장으로 대신했다. 계획서의 정밀 감지(AI 판별) 모드는 2차에서 다시 판단한다.
- 학습 데이터를 "1000개 이상"에서 "정확히 2000개"로 맞췄다.

## AI에게 맡긴 일과 내가 직접 판단한 일

**AI(Claude)에게 맡긴 일**: 라벨 세트 초안 작성, 채점 도구와 학습 스크립트, 합성·직접 쓴 학습 문장 생성, 학습 모델을 브라우저에서 돌리는 코드, 테스트 44개, 문서 작성, 결과 수치 계산.

**내가 직접 판단한 일**: 확장 방향(신호 감지 정확도 개선), 학습 방식으로 갈지와 데이터 규모(정확히 2000개), Workbench를 먼저 연결해 보기로 한 결정과 안 돼서 접은 결정, 앱을 직접 써 보고 "열린 추천이 이상하게 잡힌다"고 문제를 짚은 것과 "신호 체크가 빡빡하게 안 된다"는 평가, 열린 추천을 신호 없음으로 볼지 같은 라벨 기준(검토 중).

**AI 제안을 따르지 않은 일**: AI는 Workbench를 연결하기보다 직접 데이터를 쓰는 쪽을 먼저 권했지만, 나는 Workbench 연결을 먼저 시도하기로 했다(연결이 되지 않아서 결국 직접 쓰는 방식으로 돌아왔다). 임계값 0.4와 열린 추천 정의의 첫 안은 AI가 정한 것이고 내가 아직 확인하지 않았다.

## 다음에 할 일

1. **라벨 검토**: 라벨 116개는 AI가 초안을 썼으므로 내가 직접 보고 틀린 것을 고친다. 점수를 믿으려면 필요하다.
2. **실제 사용 문장 모으기**: 친구들이 앱에 직접 넣은 문장에서 잘못 잡히거나 놓친 것을 모아 라벨과 학습 데이터에 넣는다.
3. **남은 약점 보강**: 영어 문장의 다수 의견 오탐, "브레인스토밍이 뭐야" 같은 단어 설명 요청, 확률이 낮은 신호를 "약한 신호"로 보여 주는 방법.
4. **보류용 20개로 최종 평가**: 개선을 모두 마친 뒤 한 번만 재고, 개선이 없었던 신호는 없었다고 공개한다.
5. 정확도 보고 절을 앱 화면에 넣는다.
