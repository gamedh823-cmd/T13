# 중간 점검 2차 제출 — 신호 감지 정확도 개선

제출일: 2026-10-21 · 앱: https://gamedh823-cmd.github.io/T13/ · 소스: https://github.com/gamedh823-cmd/T13

## 이번에 만든 것 (1차 이후)

1차에서 정규식을 학습한 분류기로 바꿨다(개발용 96개에서 F1 0.82 → 0.94). 이번에는 **판정이 얼마나 믿을 만한지 측정해서 보여 주고, 측정에서 드러난 문제를 고쳤다.**

1. **확신도별 실제 정확도(보정) 측정과 "정확도 보고" 절** (`eval/report.js`, 앱 맨 아래 "판정을 얼마나 믿을 수 있나요?"): 모델이 낸 확률 구간마다 정답이 얼마나 맞았는지 개발용 + 학습에 쓰지 않은 검증 문장 462개로 쟀다. 확신도 70% 이상은 319개 중 319개(100%), 40~70%는 100개 중 86개(86%), 약한 신호 30~40%는 33개 중 20개(61%)가 맞았다. 숫자는 손으로 적지 않고 스크립트가 라벨 세트와 모델로 계산해서 화면에 그대로 보여 준다(테스트가 최신 모델과 일치하는지 확인).
2. **확신도와 약한 신호 표시**: 확정한 신호 카드에 "확신도 96%"를 붙였다. 확정 기준(40%)에는 못 미치지만 30% 이상인 신호는 버리지 않고 체크리스트에 `△`(약한 신호)로 따로 보여 준다.
3. **영어·사실 질문 오탐 보강**: 측정 중 "What is the capital of Australia?"가 다수 의견 66%, "화성의 평균 기온은 얼마야?"의 "평균"이 다수 의견 42%, "이거 어떻게 하면 좋을까?"가 열린 추천 44%로 잡히는 문제를 찾았다. 영어 일반 질문, "평균·일반적으로·보통"이 든 사실 질문, 조언을 구하는 "어떻게 하면 좋을까" 부정 문장과 영어 신호 문장 약 80개를 학습 데이터에 보강하고 다시 학습했다. 학습 데이터는 계속 정확히 2000개다(템플릿 문장을 줄여서 맞춤). 세 문장 모두 이제 신호 없음이다.
4. **"판정이 틀렸나요?" 신고 패널**: 맞는 신호에 체크하고 누르면 문장(앞 300자)·체크한 신호·앱 판정이 JSON 한 줄로 복사된다. 서버로 보내지 않고 개인정보를 지우라고 안내한다.
5. **실제 사용 문장 평가 세트**(`eval/real_use.json`): 내가 앱에 직접 넣어 본 문장 4개를 합성·AI 초안 라벨과 섞지 않고 따로 모았다. 지금 앱은 정답 신호 3개를 모두 잡았고 오탐은 없었다(4문장뿐이라 참고용).
6. 테스트 51개(core 31, eval 6, ml 10, report 4) 모두 통과.

## 확인하는 방법 (3단계 이내)

1. https://gamedh823-cmd.github.io/T13/ 에서 `What is the capital of Australia?`와 `화성의 평균 기온은 얼마야?`를 각각 `점검하기`한다. 둘 다 신호 0가지(신호 없음)면 통과(1차 모델은 다수 의견으로 잡았다). `회사에서 할 수 있는 새로운 시도가 있을까`를 점검하면 "열린 추천"이 확정(✔)되지 않고 `△`와 "약한 신호 1가지"가, `고양이 이름 후보 좀 지어 줘`를 점검하면 ✔와 "확신도 N%"가 나오면 통과.
2. 맨 아래 "판정이 틀렸나요?"에서 체크를 바꾸고 복사 버튼을 누르면 `{"text":...,"signals":[...],"앱판정":[...]}` 한 줄이 복사되고, 그 위 "판정을 얼마나 믿을 수 있나요? (정확도 보고)"를 펼치면 위 결과 표와 확신도별 정확도 표가 보이면 통과.
3. 저장소에서 `node tests/core.test.js && node tests/eval.test.js && node tests/ml.test.js && node tests/report.test.js`가 31·6·10·4개 모두 통과하는지 보고, `node eval/report.js`로 정확도 보고를 다시 만들어 화면의 숫자와 같은지 본다.

## 바뀐 점과 그 이유

- **약한 신호 기준을 20%에서 30%로 올렸다.** 2차 작업 처음에는 20% 이상을 약한 신호로 보여 주려 했다. 그런데 구간별로 정답 비율을 재 보니 20~30% 구간은 개발용에서 14개 중 1개, 검증에서 46개 중 13개(28%)만 맞아서 사실상 소음이었다. 반면 30~40%는 개발용 3개 중 2개, 검증 30개 중 18개(60%)가 맞았다. "참고용 신호"로 보여 줄 가치가 있는 구간만 남기려고 30%로 바꿨다. 이걸 재 보기 전까지는 약한 신호가 도움이 된다고 가정하고 있었다.
- **"신호 체크가 믿음직스럽지 않다"는 느낌을 숫자로 바꿔서 공개했다.** 앱을 써 보면 나아진 것을 못 느꼈는데, 원인은 점수(F1)만 있고 "이 판정을 얼마나 믿어도 되는지"를 사용자가 알 길이 없었기 때문이다. 확신도별 정확도 표를 화면에 넣었다.
- **오탐은 사용 중에 드러난 것만 보강했다.** 영어 문장, 평균·일반적으로 같은 단어, 조언 질문은 처음 만든 라벨에 없던 유형이다. 이런 오탐을 직접 찾아 학습 데이터를 보강하고 점수를 다시 쟀다.
- **정밀 감지(AI 판별) 모드는 이번에도 넣지 않았다.** 학습 모델만으로 서버 없이 동작하고, AI 호출의 비용·한도를 지고 갈 근거가 아직 없다. 최종 제출 전에 다시 판단한다.
- 계획서 2차 항목 중 "라벨 검토 반영"은 아직 하지 못했다(아래 다음에 할 일).

## AI에게 맡긴 일과 내가 직접 판단한 일

**AI(Claude)에게 맡긴 일**: 보정 측정과 정확도 보고 스크립트·화면, 확신도·약한 신호 표시, 신고 패널, 오탐 보강 학습 문장 작성과 재학습, 실제 사용 평가 세트, 테스트, 문서.

**내가 직접 판단한 일**: 앱을 써 보고 "신호 체크가 빡빡하지 않다"는 불만을 짚은 것, 1차 제출 직후 2차로 넘어간 것, "2차 제출 전에 더 나은 방향으로 고칠 수 없느냐"고 물어서 제출을 늦추고 측정부터 다시 해 본 것(그 결과 약한 신호 기준이 잘못됐다는 것을 발견했다). 라벨 기준 검토는 아직 하지 못했다.

**AI 제안을 따르지 않은 일**: 이번 구간에서는 AI 제안과 내 판단이 갈린 새 사례가 없었다(1차 제출문에 적은 사례가 마지막이다). 약한 신호 기준(30%)과 확신도 구간 나누기는 AI가 제안한 값이라 내가 아직 확인하지 않았다.

## 정직한 한계

- 이번 2차에서 점수 자체는 거의 오르지 않았다(개발용 F1 0.94 → 0.95). 한 일은 판정의 신뢰 수준을 측정·공개하고 측정에서 드러난 오탐과 잘못된 기준(약한 신호 20%)을 고친 것이다.
- **개발용 점수는 실제보다 높을 수 있다.** 임계값을 개발용 라벨을 보고 정했고, 틀린 문장을 보고 학습 데이터를 보강했기 때문이다. 보류용 20개는 아직 재지 않았다.
- 확신도 구간별 정확도는 개발용 + 검증 문장 462개로 쟀는데 대부분 합성 문장이다. 확신도 70% 이상이 100%라는 것은 합성 문장에서 그렇다는 뜻이고, 실제 사용 문장에서는 더 낮을 수 있다.
- 실제 사용 문장 평가 세트는 4개뿐이라 수치를 믿을 수 없다.
- 라벨은 AI 초안이고 사용자가 아직 검토하지 못했다.
