# 계획 설계서 v3 — 프롬프트 신호 점검기 확장: 신호 감지 정확도 개선

작성: 유지원 · v1 2026-10-19 · v2·v3 2026-10-20 · 기반 앱(T13): https://gamedh823-cmd.github.io/T13/ · 소스 https://github.com/gamedh823-cmd/T13

## v2에서 바뀐 것 (중간 점검 1차를 마치고)

- 1차에서 계획했던 라벨 세트·채점 도구·기준선을 만들었고(라벨 116개, 개발용 96·보류용 20), 기준선이 약한 곳(열린 추천 정밀도 0.63)을 확인했다.
- 원래 2차에 하려던 "규칙 개선"을 건너뛰고 **학습한 분류기**(글자 n-gram + 로지스틱 회귀)를 먼저 만들어 앱에 연결했다. 규칙을 고치면 단어 하나마다 예외가 늘어서(예: "없을까") 한계가 분명했기 때문이다. 규칙은 모델을 못 불러올 때의 대체로 남겼다.
- 학습 데이터는 정확히 2000개(합성 1432 + 직접 쓴 291 + 열린 추천 보강 277)로 만들었다.
- 정밀 감지(AI 판별) 모드는 이번에 넣지 않았고, 2차에서 다시 판단한다.

## 1. 기반 앱과 이번 확장의 문제

기반 앱(지난 과제)은 프롬프트에서 신호 8가지(토론 지시, 전문가 역할, 다수 의견, 이미지 구체성, 풀이 과정, 예시, 내 의견, 열린 추천)를 **정규식**으로 찾아 논문 결과를 보여 준다.

문제: 감지가 잘 되는지 **라벨 세트로 수치를 잰 적이 없다**(있던 테스트는 쉬운 예시 한두 개가 잡히는지 보는 것뿐). 친구가 써 보고 "토론하지 말고"가 토론으로 잡히는 오탐을 알려 줬고(부정 표현 처리로 고침), 돌려 말한 표현은 놓칠 것이다. 지금은 느낌으로 고치고 있어서, 고쳐도 좋아졌는지 알 수 없다.

## 2. 이번 확장의 목표

**신호 감지의 정확도를 측정 가능하게 만들고, 기준선보다 높인다.** 정확도 수치와 틀린 사례를 앱 안에서 공개한다.

- 누구를 위한 것인가: 프롬프트를 점검받는 사용자(잘못 잡힌 신호 때문에 엉뚱한 조언을 받지 않도록)와, 이 앱을 개발하는 나(고칠 때 개선 여부를 확인하도록).
- 핵심 기능 3가지
  1. **정답 라벨 세트**: 신호 유무를 사람이 붙인 예시 프롬프트 모음(약 100개)과 채점 도구
  2. **기준선과 개선 비교**: 현재 규칙의 정밀도·재현율을 먼저 재고, 개선판과 나란히 보여 준다
  3. **정밀 감지(선택)**: 규칙이 애매한 경우 Gemini에 판별을 맡기는 모드. 켜면 결과에 "AI가 판별"을 표시한다

## 3. 범위

**한다**
- 라벨 세트 만들기: 합성 예시(내가 쓴 것)와 친구가 써 본 실패 사례에서 개인정보를 뺀 문장. 신호별로 있는 경우·없는 경우·부정 표현·돌려 말한 표현·인용(예시로 든 문장)을 고르게 넣는다. 일부(약 20%)는 개선하기 전에 따로 떼어 두고 마지막에 한 번만 채점한다(과적합 방지).
- 채점 스크립트: 신호별 정밀도, 재현율, F1과 틀린 사례 목록. Node 한 줄로 실행된다.
- 규칙 개선: 부정·인용·변형 표현을 처리하고, 개선 전후를 같은 라벨 세트로 비교한다.
- 정밀 감지 모드: Vercel 프록시를 거쳐 Gemini 무료 API로 신호 판별을 요청하고 같은 라벨 세트로 채점한다.
- 앱 안에 "정확도 보고" 절: 측정 수치, 라벨 세트 크기, 한계를 공개한다.

**하지 않는다**
- 논문 수치를 새로 만들거나 바꾸지 않는다. 확장은 감지 정확도에 한정한다.
- 라벨 세트에 실제 개인정보나 타인의 글을 넣지 않는다.
- 결제형 API를 연결하지 않고, 입력을 서버에 저장하지 않는다.
- 정확도를 "높아졌다"고 쓸 때는 반드시 개선 전 수치와 라벨 세트 크기를 같이 쓴다.

## 4. 구조(추가분)

| 부분 | 내용 |
|---|---|
| `eval/labels.json` | 라벨 세트(프롬프트, 신호별 정답, 분류: 개발용/보류용) |
| `eval/score.js` | 채점: 신호별 정밀도·재현율·F1, 틀린 사례 출력. 규칙 감지와 AI 감지를 같은 방식으로 채점 |
| `core.js` | 규칙 감지(기준선, 모델을 못 불러올 때의 대체). 기준선은 개선 전 커밋(`175b0f1`)으로 고정 |
| `ml.js`, `train/` | 학습한 분류기를 브라우저에서 돌리는 코드(`ml.js`), 학습 데이터 2000개와 학습 스크립트, 가중치(`train/model.js`) |
| `api/detect.js` | 공개 앱의 정밀 감지용 프록시. 기존 `suggest.js`와 같은 출처 검사·분당 5회·길이 제한·무료 티어 |
| 화면 | 정밀 감지 토글, "정확도 보고" 절 |
| `tests/` | 채점 도구 자체 테스트, 부정·인용 표현 테스트 추가 |

## 5. 단계

| 단계 | 내용 | 끝났다고 보는 기준 | 상태 |
|---|---|---|---|
| 중간 점검 1차 | 라벨 세트, 채점 스크립트, 현재 규칙의 기준선 측정. 앞당겨 학습 분류기 연결까지 | 신호별 정밀도·재현율 표와 틀린 사례 목록이 있다 | 완료(2026-10-20) |
| 중간 점검 2차 | 약한 신호·확신도 표시, 틀린 판정 신고 패널, 실제 사용 문장 평가 세트(완료). 라벨 검토 반영, 약점 보강, 정밀 감지(AI 판별) 여부 결정(남음) | 개발용 세트에서 개선 전후가 비교되고, 정밀 감지를 넣더라도 실패 시 앱이 멈추지 않는다 | 진행 중(2026-10-20) |
| 최종 제출 | 보류용 20개로 한 번 채점, 정확도 보고 절 공개, 시크릿 창·새 폴더 확인 | 보류 세트 수치가 앱과 제출문에 그대로 공개되고, 개선이 없었다면 없었다고 적는다 | 예정 |

## 6. 완성의 기준

- 신호별 정밀도·재현율이 채점 스크립트로 재현된다(같은 입력이면 같은 결과).
- 규칙 개선판이 기준선보다 낫다는 것이 개발용·보류용 세트 모두에서 수치로 보인다. 나아지지 않은 신호는 그렇게 공개한다.
- 정밀 감지는 켜고 꺼도 앱이 멈추지 않고, 한도 초과·서버 실패 때 규칙 감지로 돌아간다.
- 소스와 화면에 비밀값과 실제 개인정보가 없고, 공개 URL이 로그인 없이 열린다.

## 7. 위험과 대응

| 위험 | 대응 |
|---|---|
| 라벨을 내가 붙여서 편향되거나 오류가 있음 | 라벨 기준(정의)을 `eval/README`에 적고, 애매한 사례는 "애매" 표시. 친구에게 일부를 따로 라벨하게 해서 일치율을 본다(가능하면) |
| 개선을 라벨 세트에 맞춰서 수치만 오르는 과적합 | 보류 세트를 마지막에 한 번만 채점 |
| 100개로는 신호별 표본이 작음 | 정확도 보고에 표본 크기를 표시하고, 작은 신호는 신뢰하기 어렵다고 적는다 |
| 정밀 감지 호출량·무료 한도 | 규칙이 애매한 경우에만 호출하고, IP당 분당 5회·입력 4000자 제한, 무료 티어만 사용 |
| LLM 판별이 매번 달라 재현이 안 됨 | temperature를 낮추고, 채점에는 호출 결과를 파일로 저장해 같은 결과로 다시 채점 |

## 8. 지난 앱에서 이어받은 결정

- 논문 수치는 `core.js`에만 두고 표 번호 주석을 단다.
- 선행 연구 기반 신호는 "이번 실험 아님"을 표시한다.
- Gemini 무료 API만 쓰고, 키는 Vercel 환경변수에만 둔다.
- 서버가 실패해도 앱은 멈추지 않는다.

## 8-2. v2 결정 기록 (2026-10-20)

| 결정 | 이유 |
|---|---|
| 규칙 개선 대신 학습 분류기로 교체, 규칙은 대체로 유지 | 열린 추천 오탐이 단어 하나마다 예외를 붙여야 하는 문제라서, 학습으로 문맥을 보게 함 |
| 열린 추천 정의를 "여러 선택지를 구하는 요청"으로 좁힘 | "방법이 없을까"처럼 방법·조언을 묻는 문장이 열린 추천으로 잘못 잡힘 |
| 어려운 문장 20개를 평가 라벨에 추가하고 기준선을 다시 잼 | 처음 라벨에는 이런 문장이 없어 오탐이 점수에 안 보였음 |
| 임계값 0.4 | 0.3은 F1이 조금 더 높지만 오탐이 늘어서, 엉뚱한 신호를 줄이는 쪽을 택함 |
| 학습 데이터 정확히 2000개 | 규모를 숫자로 고정해 재현성을 높임(스크립트가 합계가 2000이 아니면 멈춤) |

## 8-3. v3 결정 기록 (2026-10-20)

| 결정 | 이유 |
|---|---|
| 확률 0.2~0.4 신호를 버리지 않고 "약한 신호(△)"로 표시 | 앱을 써 보니 신호 체크가 빡빡하지 않다는 느낌이 있었고, 애매한 판정을 있다/없다로만 자르면 믿을 근거가 안 보임. 확정 기준(0.4)은 그대로라서 점수는 변하지 않음 |
| 확정 신호에 확신도(%) 표시 | 판정 근거를 보여 주기 위해 |

| 실제 사용 문장 평가 세트(`eval/real_use.json`) 분리 | 합성·AI 초안 라벨과 섞지 않고 실제 사용에서의 성능을 따로 보려고 |

## 9. 처음 해 볼 일 (v1 기록, 1·2·3은 완료)

1. 신호 정의와 라벨 기준을 한 장으로 정리한다.
2. 라벨 세트 초안 50개를 쓴다(신호별 있음/없음, 부정, 인용, 돌려 말함을 골고루).
3. `eval/score.js`로 현재 규칙의 기준선을 잰다. 이 결과를 보고 2차 계획을 고친다(새 버전으로 저장).
